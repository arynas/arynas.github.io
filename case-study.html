Making small models work for Indonesian agentic AI

PT Atmatech Global Informatika (Netray) · 2025–2026 · Role: led the program and contributed to evaluation design, data iteration and integration review

The problem

Netray analyzes Indonesian news and social media. We wanted a chat assistant that could answer questions like "rangkum isu X di media sosial minggu lalu" ("summarize issue X on social media last week") by calling the right tools: search, query the analytics database, and recap the results.

We explored whether small, local models could handle this reliably, so the evaluation also had to cover inference cost and hardware. Small models have well-known weak spots in function calling, and Indonesian makes them worse. Two failure types turned out to matter most:

  • Calling a tool when none is needed, for example answering "halo" with a database query.
  • Getting the arguments wrong, especially relative dates like "minggu lalu" (last week) or "bulan ini" (this month).

What we did

1. Built an evaluation before choosing a model

We designed test cases around the decisions an agent actually makes:

DimensionWhat we tested
Tool needShould the model call a tool at all? This includes greetings and small talk (no-tool behavior).
Tool choiceDid the model pick the right tool?
ArgumentsWere the keywords, entities and parameters correct?
TimeDid explicit and relative dates, weekly ranges and monthly ranges resolve correctly?
DeploymentHow do quantization, serving backend, and CPU versus GPU affect speed and memory?

The evaluation grew to 51 populated model and configuration sheets across several small and local model families.

2. Adapted a small model to Indonesian

  • Translated an English function-calling dataset to Indonesian through a local API, with checkpoint and resume.
  • Cleaned the result with deduplication and MetricX-assisted quality filtering. The project log reports 59,266 of 60,000 rows kept (98.8%). That figure is data retention, not model accuracy.
  • Fine-tuned xLAM-2-1B with LoRA SFT, then added targeted greeting (no-tool) and date-range examples wherever the evaluation showed failures.
  • Designed serving on vLLM with an OpenAI-compatible API.

3. Tested the full loop, not just the JSON

In an MCP-based research assistant, we evaluated function calls on their own and also end to end: tool call, then the database or search result, then the final answer. The work covered news and social-media recaps and analytics query adjustment.

What we learned

  • Valid JSON is not task completion. A model can choose the right tool and still fail on arguments, dates, or on how it uses the tool result. Most of our tests measured function-call generation, so we tracked end-to-end completion separately and didn't mix the two numbers.
  • Targeted data beats more data. Adding greeting and weekly-range examples improved greeting and some weekly cases. Monthly date ranges stayed an open problem, and we report it as one.
  • Evaluation decides deployment. Quantization, backend and hardware choices changed speed and memory enough to affect which model we would ship. They were tested alongside quality, not after it.
  • Know what a result can't prove. Internal scores are not a public benchmark, so we don't present them as one.
